# 一、本讲在整套课程中的位置

第01讲不是“Python知识点第一课”，而是整套课程的**程序认知入口**。

后面的变量、分支、循环、函数，本质上都依赖一个最基础的认识：

> **程序是由明确指令组成的，计算机会按照确定规则和执行顺序运行这些指令。**

如果这一层没有建立，学生后面很容易形成一种错误的“看代码方式”：

- 看代码像看一整张图片；
- 凭感觉猜结果；
- 忽略执行顺序；
- 认为计算机会“理解自己的意思”；
- 出错时只觉得“电脑怎么没按我想的做”。

因此，本讲真正的任务不是教多少语法，而是建立：

> **程序 → 指令 → 执行 → 结果**

这一条最小闭环。

# 二、本讲核心定位

## 一句话定位

> **让学生第一次真正意识到：计算机不会猜人的意思，只会按照明确的程序指令和确定的顺序执行。**

# 三、本讲为什么现在教

这是全课程第一讲，学生还没有任何正式 Python 前置知识。

因此不能直接把课程起点设成：

```python
print("Hello")
```

然后开始解释括号、引号、函数。

那样学生学到的首先是：

> “Python 第一条语法长这样。”

而不是：

> “我为什么需要写代码？”

本讲应该先解决四个根问题：

1. 什么是程序？
2. 为什么计算机需要明确指令？
3. 编程语言在“人”和“计算机”之间做什么？
4. 代码为什么存在执行顺序？

这些问题一旦建立，第02讲的 `print()` 才会有真正的位置：

> **既然程序会执行指令，那么我们怎样让程序把信息显示出来？**

# 四、本讲入口认知

学生可能存在以下不同经验：

- 完全没有编程经验；
- 学过 Scratch 等图形化编程；
- 玩过机器人、积木编程；
- 自己接触过一点 Python；
- 只知道“Python是一门编程语言”。

本讲不能依赖任何一种经验作为必要前置。

同时，对于学过 Scratch 的学生，也不能把本讲变成重复的“什么是编程”。

需要把认知提升到：

> **无论积木还是文字代码，本质都在给计算机描述可执行的规则。**

---

# 五、本讲必须建立的核心认知

本讲只需要真正建立四个核心认知。

---

## 核心认知1：计算机不会“理解你的意思”

人类可以接受模糊表达。

例如：

> “往前走一点。”

人会根据环境猜：

- 多远算一点？
- 往哪个方向？
- 什么时候停？

但程序中的指令必须尽量明确。

课程要让学生形成：

> **程序不是“告诉电脑我想要什么”，而是“把执行规则写清楚”。**

这是后续：
- 条件；
- 循环；
- 算法；
- Debug；

共同的思想地基。

---

## 核心认知2：程序是一组可执行的指令

不要求学生背教科书定义。

学生最终能用自己的话说清：

> 程序就是让计算机按规则完成事情的一组指令。

即可。

重点在“可执行”，不是定义措辞。

---

## 核心认知3：代码存在执行顺序

例如教师提供预写代码：

```python
print("第一步")
print("第二步")
print("第三步")
```

本讲允许学生**体验性运行**这段代码。

但注意：

> `print()` 在第01讲只作为“已经准备好的输出指令”使用，**不正式教授语法结构**。

学生此时只需要观察：

> 第一行先执行，然后第二行，再第三行。

可以进一步改变三行顺序，观察结果同步改变。

这一步非常重要。

它为后面的：

- 连续赋值；
- if 路径；
- 循环轮次；
- 函数调用；

提前建立“执行流”意识。

---

## 核心认知4：写代码需要经历“写 → 运行 → 看结果 → 修改”

学生第一次接触 Python 时必须建立一个正常工作循环：

> **写代码 → 运行 → 看结果 → 修改 → 再运行**

而不是：

> 老师写完 → 学生抄完 → 成功一次 → 结束。

第一讲就应该让学生至少经历一次：

> **修改一处 → 重新运行 → 观察变化。**

这也是后续 Debug 的最早雏形。

---

# 六、本讲知识结构

本讲知识链建议固定为：

> **现实中的指令**
>
> ↓
>
> **明确与模糊的区别**
>
> ↓
>
> **程序是一组明确、可执行的指令**
>
> ↓
>
> **编程语言是描述这些指令的一种方式**
>
> ↓
>
> **Python 是我们接下来使用的编程语言**
>
> ↓
>
> **代码会被程序按顺序执行**
>
> ↓
>
> **写 → 运行 → 观察 → 修改**
>
> ↓
>
> **完成第一次真正的 Python 运行体验**

这条链不能被大量“计算机百科知识”打断。

# 七、本讲核心问题链

Gemini 后续进行教学设计时，应围绕以下问题推进，而不是直接讲定义。

## Q1
> 如果我只说“帮我把这件事做好”，计算机知道该怎么做吗？

目标：
制造“指令必须明确”的需求。

---

## Q2
> 如果想让计算机完成一件事，我们究竟要给它什么？

目标：
引向“可执行步骤 / 指令”。

---

## Q3
> 一堆指令写出来以后，计算机会同时做，还是有顺序地做？

目标：
建立执行顺序。

---

## Q4
> 如果把两条指令的位置换掉，结果会不会改变？

目标：
通过可观察实验建立“代码顺序会影响结果”。

---

## Q5
> 程序第一次没有按我们预期运行，是电脑坏了吗？

目标：
建立最早期 Debug 态度：

> 先检查指令和代码。

不要求本讲正式学习错误类型。

# 九、“体验性出现”和“正式教学”的边界

这是本讲非常重要的课研边界。

## 可以

教师说：

> “这一行现在先把它当成一个‘让电脑显示一句话’的指令，我们下一讲再正式拆它。”

然后学生运行和修改。

## 不可以

- `sep`；

否则第01讲会迅速从“程序认知”滑成“print语法课”，破坏课次结构。

# 十一、本讲程序思维训练点

本讲虽然语法极少，但程序思维并不少。

核心训练有三个。

## 1. 指令明确性

从：
> “我知道你什么意思”

切换到：
> **“计算机能不能只根据这条指令准确执行？”**

---

## 2. 执行顺序

学生开始习惯：

> **先看第一步执行什么，再看下一步。**

这是以后 Trace 的种子。

---

## 3. 结果来自指令

程序结果不是魔法。

> **结果是代码执行过程产生的。**

改变代码，结果可能改变。

---

# 十二、本讲题型设计

本讲不是传统刷题课，但依然需要形成“基础 → 同构 → 变式 → 小综合”的认知递进。

---

## 1. 基础：判断指令是否明确

例如：

A：
> 往前走。

B：
> 向前走3步。

让学生判断哪一个更容易被严格执行。

重点不是生活常识，而是“明确性”。

---

## 2. 同构：给步骤排序

例如一个非常简单的现实过程：

> 打开水杯 → 倒水 → 喝水

打乱顺序，让学生排序。

目标：

> **步骤顺序可能影响结果。**

注意不要把这一活动拖成低幼游戏。

---

## 3. 代码观察：预测输出顺序

给出教师预写代码：

```python
print("A")
print("B")
print("C")
```

问：

> 会按照什么顺序出现？

运行验证。

---

## 4. 变式：调换代码

```python
print("B")
print("A")
print("C")
```

先预测，再运行。

目标：

> **先想，再验证。**

---

## 5. Debug雏形：找出“程序为什么没按预期做”

不正式讲 SyntaxError。

只给非常简单、可观察的问题，例如：
- 两行顺序写反；
- 某句文字写错；
- 漏了一行教师给出的预写指令。

学生进行：
> 观察 → 找差异 → 修改 → 再运行。

---

# 十三、本讲课堂活动类型

本讲适合：

# 十四、80分钟教学容量设计

> 这里是课研时间预算，不是要求 Gemini 按分钟机械执行。

| 教学模块 | 建议有效时间 | 主要任务 |
|---|---:|---|
| 认知引入 | 8～10分钟 | 明确指令 vs 模糊指令，建立问题 |
| 程序与编程语言 | 8～10分钟 | 程序、代码、Python的关系 |
| 第一次运行体验 | 12～15分钟 | 打开环境、运行预写代码、观察结果 |
| 执行顺序实验 | 12～15分钟 | 预测、调换代码、再次运行 |
| 修改与简单Debug | 12～15分钟 | 修改文字/顺序、观察错误或结果变化 |
| 独立小任务 | 10～12分钟 | 学生独立完成一次“修改→预测→运行” |
| 收束与出口检查 | 6～8分钟 | 用学生自己的话解释程序与执行 |

总计约：

> **68～85分钟**

实际教学按约80分钟动态调整。

其中必须优先保留：

1. 第一次运行；
2. 执行顺序实验；
3. 独立修改；
4. 出口检查。

如果现场设备或登录耗时较长，应削减背景介绍，而不是削减学生操作与思考时间。

# 十六、本讲能力出口

课程结束时，学生应至少能够独立做到以下事情。

## 必须做到

### 1.
能用自己的话说明：

> 程序是让计算机按照明确规则执行的一组指令。

措辞不要求完全一致。

### 2.
知道代码存在执行顺序。

### 3.
面对三行极简预写代码，可以先预测基本执行顺序，再运行验证。

### 4.
可以独立完成：
> 修改一处代码 → 运行 → 观察变化。

### 5.
程序结果与预期不同时，知道第一反应应该是：
> 检查自己的指令/代码。

而不是认为计算机会自动理解意图。

- 独立默写 `print()`；
- 准确定义字符串；
- 理解函数；
- 写变量；
- 输入数据；
- 写算法。

# 二十、本讲给第02讲留下的接口

第01讲结束时，学生脑中应该自然留下：

> **程序能执行代码。**

但还没有正式解决：

> **一条 Python 指令究竟怎样把信息显示出来？**

因此第02讲自然承接：

# 第02讲｜输出与基本数据：让程序表达信息

下一讲正式拆解：

```python
print("Hello")
```

并进入：

- `print()`；
- 字符串；
- 数值；
- 引号；
- 多条输出。

这样第02讲不是突然出现一个陌生语法，而是在回答第01讲已经产生的问题。

# 二十二、本讲最终课研结论

第01讲的价值不在于“学会多少 Python”。

它负责建立整套课程第一个真正的底层模型：

> **计算机不会猜。程序由明确指令构成。代码按照顺序执行。结果来自执行过程。**

这四件事站住以后，第02讲开始正式进入 Python 语言才有意义。

# 最终一句话

> **第一讲不是教孩子背第一条Python语法，而是让孩子第一次真正用“程序会怎样执行”的眼睛看代码。**
